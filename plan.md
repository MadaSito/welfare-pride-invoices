# Welfare Pride Invoices — Implementation Plan

## Product scope

Build a secure, multi-tenant operational invoicing application with **Welfare Pride** as its default tenant and design language. The product will provide an authenticated invoice workspace, a tenant/company address book, invoice lifecycle controls, branded PDF rendering, and audit-ready delivery through an administrator-selected **Microsoft Graph API** or **SMTP** transport.

The implementation uses a standalone React + Express + tRPC + Drizzle/MySQL application. Application-owned opaque sessions, local authentication, TOTP MFA, and optional Welfare Pride SSO provide login and session validation. The application owns tenant membership and roles, and every tenant-scoped query is authorized on the server. Platform administrators may create companies, grant tenant-level roles, and configure protected delivery settings.

The master prompt contains additional enterprise deployment and integration directions. This delivery will implement the working invoicing core and its secure extensibility points: HMAC-signed webhook verification, structured audit records, server-side rate limiting, Cloudflare-aware request handling, restricted storage uploads, and deployable Node/Docker/Hostinger documentation. Entra ID, Google, SAML 2.0, and TOTP need the organization’s identity-provider metadata and cannot truthfully be enabled without it; the implementation will retain a documented identity-integration boundary rather than simulate those controls.

## Key outcomes

1. **Authenticated multi-tenant workspace.** The dashboard will show invoice performance and recent delivery activity. Server-side role checks will distinguish `platform_admin`, `company_creator`, and `company_viewer`, with a company membership record as the tenant boundary.
2. **Invoice and address-book lifecycle.** Users with creator/admin access can manage contacts and invoice drafts, including structured line items, quantity, unit price, configurable tax/discount, notes, terms, payment instructions, due date, and client selection. Viewer users will be able to view and download only their permitted company invoices.
3. **Branded PDF invoices.** A server-only PDF service will embed locally supplied Roboto fonts, tenant/company contact details, normalized line items, tax/discount calculations, terms, payment instructions, and a proper company logo. Logo placement will use a bounded *contain* box with a configurable scale setting, preserving the aspect ratio and preventing oversized or distorted logos. A printable Welfare Pride letterhead preview will accompany the default brand package.
4. **Company branding administration.** Admins will set company name/contact information, colors, document footer, invoice logo scale, and optional logo alignment. The upload flow will validate ownership, MIME type, byte size, and image dimensions before storing a tenant-prefixed object key. The branding screen will include an immediate invoice-header preview so administrators can see the result before saving.
5. **Administrator-selected email delivery.** A delivery settings page will allow an administrator to select either:
   - **Microsoft Graph API** using tenant ID, application/client ID, application secret, sender mailbox, and configured display name; and
   - **SMTP** using host, port, TLS mode, username, password, from address, and configured display name.

   Credentials will be encrypted at rest using an application-held AES-256-GCM key and never returned to the browser. The configured provider will send a branded HTML summary with the invoice PDF attached, honor an optional BCC archive address, persist `queued`, `sent`, or `failed` audit results, and show an Admin **Email logs** page. Graph settings will include the requested **Send Test Email** action to verify the sender connection and configured display name. Successful end-to-end delivery requires the administrator to later supply real provider credentials and grant the Graph app `Mail.Send` application permission for the sender mailbox.
6. **Security, observability, and webhooks.** All mutation inputs will be schema-validated; unsafe status transitions will be prevented; database rows will be scoped to the company membership; sensitive routes will be rate-limited; and audit events will capture actor, tenant, resource, request correlation identifier, and outcome. A raw-body HMAC-SHA256 webhook verification endpoint will be included with a timestamp/replay window and a protected secret configuration requirement. CORS/CSP/cookie settings will preserve the managed Preview login behavior.
7. **Deployment and source control.** The repository will remain Docker-ready, expose an unauthenticated health path, honor `PORT`, and include deployment notes for Hostinger Node/Passenger, Docker Compose/VPS, and Cloudflare proxy/WAF configuration. On completion the project will be connected to a new private GitHub repository through the managed GitHub transfer flow and pushed to `main` after the user confirms the repository card.
8. **Recurring invoices, approval, and send-time numbering.** Invoice creators and company administrators will be able to save daily, weekly, monthly, six-monthly, or yearly invoice templates with a UTC delivery time, recipient, due-days, line items, taxes, terms, and payment instructions. Six-monthly schedules select an anchor month (January–June) and day, then recur in that month and six months later; yearly schedules select a month and day. Server validation, cron generation, scheduler next-run calculation, and durable occurrence keys use the same explicit cadence model. The persisted scheduler-selected occurrence instant anchors each run key and scheduled issue date so delayed callbacks do not cross a day, month, or year boundary; scheduled creation also reasserts the active unarchived schedule inside its invoice transaction. A review-first schedule creates an `awaiting_approval` document, visible in the recurring workspace and invoice list; only a tenant-scoped creator/administrator approval transitions it to finalized and eligible for delivery. Each review-first schedule also offers a visible **Generate for review** action that creates one pending manual-review invoice without changing its next scheduled run, then shows the PDF review and approval controls. Auto-send remains an explicit encrypted-provider opt-in. Platform/service-owned Heartbeat jobs authenticate each callback, resolve the schedule exclusively by the scheduler-issued task UID, and use a durable per-occurrence run ledger with a recoverable lease and invoice link to prevent duplicate documents. Drafts use a clearly provisional reference; one-off invoices allocate the company `PREFIX-YEAR-NNNN` counter on their first actual send, while each recurring template owns an independently protected prefix and next number, such as `HPP035`. A company administrator can migrate either the company one-off counter or a recurring project/schedule series with server-side bounds, transactional concurrency protection, audit logging, and no-backward safeguards after a local financial invoice is issued. Archived templates remain inactive but retain their series reservation and historical invoice/run relationships. A durable outbox enters an explicit uncertain state before provider dispatch and blocks automatic resend until an administrator reconciles the outcome; an allocated number is never reused.

9. **Standalone Hostinger identity and service cutover.** Before legacy identity removal, a bootstrap local `admin@welfarepride.local` platform-administrator account is inserted with a generated one-time password, `mustChangePassword`, and MFA enrollment required. The application replaces platform JWTs with rotating opaque database sessions, CSRF-protected cookie-authenticated mutations, scrypt password hashes, encrypted RFC 6238 TOTP seeds, hashed recovery codes, account/session revocation, and a no-token-persistence browser flow. The MFA enrollment screen renders a client-side QR code exclusively from the authenticated server-issued `otpauth://` URI and retains a copyable base32 secret as the manual fallback; neither value is logged or persisted in browser storage. Microsoft Entra uses Authorization Code + PKCE with state/nonce records, discovery/JWKS validation, an exact configured callback, tenant/audience checks, and link-only matching through tenant/object ID. A platform-admin lifecycle console creates and disables local or Entra accounts, creates one-time local passwords, manages membership/revocation, resets MFA/recovery data, and revokes sessions with immutable audit events. Platform OAuth/SDK/public config/preview fallback/notifications/Heartbeat are removed. A host cron calls an HMAC-authenticated internal dispatcher that retains the existing run lease/idempotency semantics, and durable logos use S3-compatible environment-configured storage. Deployment documentation is rewritten for Hostinger Node.js with no platform runtime dependencies.
9. **Reversible administrative removal.** Draft invoices may be explicitly discarded only before finalization and before a financial document number is assigned; the operation is tenant-scoped, audit logged, and never applies to finalized or delivered documents. Companies are archived rather than deleted: archival locks and marks the company first, refuses while a delivery is actively in progress, and requires in-transaction active-company assertions for new invoice, discard, finalize, and send claims. It hides a tenant from normal portal selection, blocks ordinary operations and recurring scheduler creation, deactivates schedules without losing records, and retains all financial/audit data. Company administrators who retain membership can list and restore archived tenants; restoration never auto-enables scheduled billing.
10. **First-run configuration, backups, and delivery operations.** After bootstrap local-admin password change and MFA, a dedicated first-run setup workspace will verify the host-managed 32-byte encryption-key health and guide the administrator to company brand/logo/colors, optional Welfare Pride SSO, Graph/SMTP connection, mail templates, and backup destinations. The root encryption key cannot be safely persisted through the browser—it remains in Hostinger environment configuration—while ordinary SSO, mail, and backup destination secrets are encrypted in database configuration. Mail templates will support a constrained documented variable set; all send attempts and explicit administrator resends will be recorded as immutable log attempts. Platform administrators can download a data export or encrypt and upload a portable backup archive to Amazon/Wasabi/Backblaze S3-compatible storage or SharePoint Graph document libraries. SharePoint destinations resolve a normal HTTPS global-Microsoft-365 site URL through the configured Graph application to a site ID and available libraries, canonicalize encoded pasted names exactly once, follow only bounded trusted Graph pagination, and use a server-validated folder browser/click-to-select breadcrumbs rather than exposing raw Graph identifiers as the primary workflow. Every browse/test/upload reasserts that its drive belongs to the chosen site and its selected path is a folder; browse audits retain safe counts/depth only. Exports omit credentials, password hashes, MFA/recovery materials, and live sessions; cloud backup runs and connection tests are fully audited.

11. **Portable deployment and source hygiene.** The deployable source tree will contain only the standalone Welfare Pride Node.js application, its database migrations, and production artifacts. Remaining managed-platform metadata, legacy types, debug configuration, and route manifests will be removed. A complete Hostinger Node.js Web App guide will specify Node 22, pnpm, the repository root/`main` branch, the production build/migration/bootstrap sequence, the `dist/index.js` entry point, server-side environment variables, and post-deployment setup. A safe interactive installer selector plus native Node.js, Docker Compose, and Docker-with-MySQL paths will make repeatable VPS operation possible without embedding generated secrets or provider credentials in source. The first bootstrap administrator is created only when absent and must change its password and enroll MFA before operational access.

12. **Administrator-managed Microsoft Clarity.** The official Clarity browser package will be loaded only after a public, enabled project identifier is fetched from the standalone application. The identifier is validated and encrypted at rest in application settings, configured only by a platform administrator in Security & access, and changes are audit-logged. The public configuration endpoint exposes no administrative data; it returns only an enabled project ID, which is inherently required in the browser for Clarity initialization. The UI will clearly call out the external telemetry/privacy boundary and let an administrator disable tracking without a deployment.

13. **One-command Ubuntu VPS bootstrap.** A separate privileged installer will target Ubuntu/Debian only and offer native Node.js 22 or Docker Compose operation. It will install only missing prerequisites, create a dedicated non-root application account, clone or fast-forward the selected repository branch, prepare a mode-specific `.env` without printing supplied credentials, and generate missing cryptographic/database secrets locally. Native mode provisions a local MySQL-compatible server and limited loopback database account by default, with explicit `--database external` opt-in for a remote connection; Docker Compose provisions its own persistent local MySQL. It will run additive migrations and the idempotent bootstrap-admin command exactly once per initial account, preserving later passwords and MFA. Native mode installs a systemd service running Node directly as the non-root account; both modes configure a Cloudflare-aware Nginx proxy, trust real visitor IPs only from published Cloudflare networks, and keep Docker’s listener loopback-only. An optional firewall mode restricts HTTP/HTTPS to Cloudflare ranges while retaining SSH. TLS remains an explicit post-DNS origin-certificate step. The installer must stop rather than overwrite a non-fast-forward worktree or existing configuration.

## Design direction — Welfare Pride operations console

- **Design movement:** A purpose-built, editorial operations console rather than a generic SaaS dashboard: clear hierarchy, practical density, and deliberate whitespace.
- **Core principles:** Credible and calm; transaction-focused; highly legible; accessible in routine administrative use.
- **Color philosophy:** Welfare Pride blue (`#5A92C9`) provides the steady structural field, orange (`#D58240`) is reserved for decisive financial attention and action, while white and near-black preserve document-grade clarity.
- **Layout paradigm:** A compact left navigation rail pairs with a broad, document-like work canvas. The invoice composer uses a structured two-column working surface with live totals and branded output evidence rather than a card grid of unrelated widgets.
- **Signature elements:** A slim Welfare Pride blue top band; orange status accents and due-date signals; subtle dotted/patterned blue surfaces inspired by the supplied brand guide; carefully bounded logos in document previews.
- **Interaction philosophy:** Keep administrative actions explicit. Users see calculations before save, delivery/provider configuration before a send, and brand changes in a live header preview before publishing them to invoices.
- **Animation:** Fast 150–220 ms opacity/position transitions only for navigation, side panels, and feedback. Never animate invoice values or delivery status changes ambiguously.
- **Typography system:** The supplied Roboto family is embedded locally. Headings use Roboto Bold/SemiBold with compact tracking; operational body and invoice copy use Roboto Regular/Medium; monetary totals use tabular numerals where available.
- **Brand essence:** “Welfare Pride Invoices gives organizations a precise, trustable way to create and deliver branded financial documents.” Personality: warm, accountable, organized.
- **Brand voice:** Direct and considerate. Examples: “Ready to send when you are.” and “Your client will receive a branded PDF and a complete delivery record.”
- **Wordmark & logo:** The supplied Welfare Pride logo remains the primary mark; no substitute wordmark will be invented. It will be preserved at original aspect ratio across web, document, and thumbnail placements.
- **Signature brand color:** Welfare Pride blue `#5A92C9`.

## Data and service design

- `companies`: branding, address/contact data, footer, invoice sequence, invoice logo sizing settings, and default delivery preferences.
- `company_members`: tenant membership and a constrained company role.
- `contacts`: address book records, scoped to one company.
- `invoices` / `invoice_line_items`: immutable finalized invoice data, generated invoice number, amount fields in minor currency units, status, and delivery timestamps.
- `email_provider_configs`: company configuration metadata and AES-GCM encrypted connection payload (never sent back to the client).
- `email_templates`: company-scoped subject and HTML body template plus actor/update metadata; variables resolve only server-side at delivery time.
- `email_logs`: provider, recipient, BCC state, invoice reference, status, response summary, correlation ID, and timestamps.
- `backup_destinations` / `backup_runs`: platform-admin encrypted destination records, provider health/test data, immutable upload attempt history, safe archive identifiers, and outcome/actor metadata.
- `audit_logs`: structured change/event history scoped to tenant and actor.
- `webhook_events`: protected inbound-event receipt data and replay token/key material reference.
- `recurring_invoice_schedules` / `recurring_invoice_line_items`: tenant-scoped recurring template, cadence, UTC run time, next callback state, optional automatic delivery, and immutable schedule line items.
- `recurring_invoice_runs`: unique schedule-occurrence ledger used to make scheduler retries idempotent and retain the resulting invoice and safe status summary.

The PDF generator, logo-storage service, encryption helper, delivery adapters, HMAC verifier, audit service, and request security middleware will be isolated under `server/services/` and `server/security/`. This prevents the UI from owning secrets or business-critical authorization logic.

## Dependencies and operational constraints

The build will add only the production dependencies needed for server PDF generation, SMTP delivery, image validation, and encryption-compatible handling. Provider credentials will be introduced through protected platform secrets after the code is ready; they will not be committed or written to `.env` files. The tenant-held provider payload will additionally require a runtime `APP_CONFIG_ENCRYPTION_KEY` for encryption. The app will present a secure configuration state rather than falsely claiming live email delivery until those credentials are supplied.

Invoice sending is an external action. The user has authorized building the capability; actual outbound test and client email messages will only be initiated by an authenticated administrator inside the application after provider configuration.

The initial platform-administrator session will display a guided setup checklist for company branding, the branded Welfare Pride Single Sign On (SSO) configuration, and Graph/SMTP delivery. Entra tenant/client credentials can be supplied through the administrator-only Security & access panel and are encrypted at rest using the server key; Hostinger environment variables remain a supported immutable fallback. The initial setup marker is explicit and does not auto-provision external identities.
